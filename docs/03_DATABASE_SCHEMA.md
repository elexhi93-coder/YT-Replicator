# 03 — Database Schema

**Project:** YT-Replicator · **Engine:** PostgreSQL 16 · **Status:** Draft
**Depends on:** `02_DOMAIN_MODEL.md`

---

## 1. Ownership rule: one source of truth

**Engine: PostgreSQL 16 (D8).** Chosen for multi-worker concurrency, atomic job
claims with `FOR UPDATE SKIP LOCKED`, real `timestamptz`, and managed backups —
and because it removes the legacy's worst failure mode, four processes sharing a
single bound SQLite file (D-19). SQLite would be adequate for a single worker and
is deliberately not used, so that no part of the design depends on a deployment
being small.

**Django models and migrations are the source of truth.** The SQL in this
document is the *result* of those models, written out so a human can review the
design without running code.

Three artefacts must never disagree:

1. the Django models,
2. the generated migrations,
3. this document.

A change that touches one without the others is an incomplete change. This rule
exists because the legacy's documents and code disagreed inside the same
release (D-01, D-27), and "LOCKED" in a header meant nothing.

If the SQL here ever differs from what a migration produces, the migration wins
and this file is corrected in the same commit.

## 2. Conventions

| Concern | Decision | Why |
|---|---|---|
| Primary keys | `bigint GENERATED BY DEFAULT AS IDENTITY` | Simple, fast, readable in logs. A `public_id uuid` can be added later without touching relationships; opaque IDs are not a security control — workspace scoping is. |
| Timestamps | `timestamptz`, UTC in storage | The legacy stored naive ISO strings and then got the quota reset boundary wrong (D-03). One type, no ambiguity. |
| Booleans | real `boolean` | No `0`/`1` integers. |
| Enumerations | `text` + `CHECK (col IN (…))` | Adding a value is a one-line migration. Postgres enum types add ceremony for the same result. |
| JSON | `jsonb`, only for genuinely schema-less payloads | Never for state that must be queried or constrained. The legacy kept its backfill queue in JSON and could not query it (F-04). |
| Bytes and counts | `bigint` | |
| Table naming | `snake_case`, singular | `delivery`, not `deliveries`. One row, one name. |
| Soft delete | `deleted_at timestamptz NULL` on configuration entities only | `pipeline`, `source`, `destination`. History tables are never deleted. |
| Tenant scoping | `workspace_id` on every tenant-scoped table, with scoped unique constraints | D11. No query crosses tenants by accident. |
| Deletion policy | Configuration cascades with its workspace; **history never cascades** | Delivery, attempt, inventory, media and audit rows must be purged deliberately. This is INV-4 and it fixes D-04. |
| Indexing | an index for every foreign key used in a filter, plus composite uniques | |

`auth_user` is Django's built-in user table and is not redefined here.

Table inventory, in the order this document defines them:

| Group | Tables |
|---|---|
| 1 · Tenancy and settings | `workspace`, `workspace_member`, `app_setting` |
| 2 · Credentials | `google_client`, `authorized_channel` |
| 3 · Sources and catalog | `source`, `catalog_video` |
| 4 · Pipelines | `download_profile`, `pipeline`, `pipeline_source`, `destination`, `pipeline_destination` |
| 5 · Work | `job` |
| 6 · Delivery truth | `delivery`, `delivery_attempt`, `destination_inventory`, `quota_usage` |
| 7 · Media and storage | `storage_root`, `media_asset`, `media_event` |
| 8 · Operations | `worker_heartbeat`, `audit_event` |

## 3. Group 1 — Tenancy and settings

```sql
CREATE TABLE workspace (
    id          bigint GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    name        text        NOT NULL,
    slug        text        NOT NULL UNIQUE,
    is_active   boolean     NOT NULL DEFAULT true,
    created_at  timestamptz NOT NULL DEFAULT now(),
    updated_at  timestamptz NOT NULL DEFAULT now()
);

CREATE TABLE workspace_member (
    id            bigint GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    workspace_id  bigint      NOT NULL REFERENCES workspace(id) ON DELETE CASCADE,
    user_id       bigint      NOT NULL REFERENCES auth_user(id) ON DELETE CASCADE,
    role          text        NOT NULL
                  CHECK (role IN ('owner', 'operator', 'viewer')),
    created_at    timestamptz NOT NULL DEFAULT now(),
    UNIQUE (workspace_id, user_id)
);
CREATE INDEX workspace_member_user_idx ON workspace_member (user_id);
```

Roles in v1 are deliberately coarse: `owner` manages credentials and members,
`operator` runs pipelines and queues work, `viewer` reads. Finer permissions
are a v2 concern.

`app_setting` is deliberately **not** tenant-scoped: it holds deployment
concerns such as the free-space floor, the retention backstop, poll intervals
and the reconciliation cadence.

```sql
CREATE TABLE app_setting (
    key         text        PRIMARY KEY,
    value       jsonb       NOT NULL,
    updated_at  timestamptz NOT NULL DEFAULT now()
);
```

## 4. Group 2 — Credentials

Secrets are stored encrypted (`bytea`), never as plaintext text. The encryption
key lives in the environment, **not** in this database, and must be backed up
alongside it — lose the key and the tokens are unrecoverable. This fixes D-11
(plaintext token columns) and D-22 (tokens written into an export file).

```sql
CREATE TABLE google_client (
    id                bigint GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    workspace_id      bigint      NOT NULL REFERENCES workspace(id) ON DELETE CASCADE,
    label             text        NOT NULL,
    client_id         text        NOT NULL,
    client_secret_enc bytea       NOT NULL DEFAULT ''::bytea,
    daily_upload_cap  integer     NOT NULL DEFAULT 6 CHECK (daily_upload_cap > 0),
    is_active         boolean     NOT NULL DEFAULT true,
    created_at        timestamptz NOT NULL DEFAULT now(),
    updated_at        timestamptz NOT NULL DEFAULT now(),
    UNIQUE (workspace_id, client_id),
    UNIQUE (workspace_id, label)
);
CREATE INDEX google_client_active_idx ON google_client (workspace_id, is_active);
```

One client is one Google Cloud project. Rotation, when needed, happens only
across **dedicated** projects bound to their own channels — never globally
(D-23).

```sql
CREATE TABLE authorized_channel (
    id                bigint GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    workspace_id      bigint      NOT NULL REFERENCES workspace(id) ON DELETE CASCADE,
    google_client_id  bigint      REFERENCES google_client(id) ON DELETE SET NULL,
    channel_id        text        NOT NULL,               -- UC…
    title             text        NOT NULL DEFAULT '',
    access_token_enc  bytea,
    refresh_token_enc bytea,
    token_expires_at  timestamptz,
    scopes            text[]      NOT NULL DEFAULT '{}',
    token_state       text        NOT NULL DEFAULT 'missing'
                      CHECK (token_state IN
                        ('missing','valid','expiring','invalid','revoked')),
    last_checked_at   timestamptz,
    last_error        text        NOT NULL DEFAULT '',
    created_at        timestamptz NOT NULL DEFAULT now(),
    updated_at        timestamptz NOT NULL DEFAULT now(),
    UNIQUE (workspace_id, channel_id)
);
CREATE INDEX authorized_channel_state_idx
    ON authorized_channel (workspace_id, token_state);
```

`ON DELETE SET NULL` on the client is deliberate: removing a Google client must
not destroy the channel record or its tokens. The channel then visibly reports
that it needs a client again — a fixable state rather than a lost credential.

## 5. Group 3 — Sources and catalog

```sql
CREATE TABLE source (
    id              bigint GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    workspace_id    bigint      NOT NULL REFERENCES workspace(id) ON DELETE CASCADE,
    kind            text        NOT NULL CHECK (kind IN ('channel','playlist')),
    external_id     text        NOT NULL,        -- UC… or PL…
    url             text        NOT NULL,        -- exactly as the operator typed it
    name            text        NOT NULL DEFAULT '',
    is_active       boolean     NOT NULL DEFAULT true,
    scan_status     text        NOT NULL DEFAULT 'never'
                    CHECK (scan_status IN
                      ('never','scanning','ok','partial','error')),
    last_scan_at    timestamptz,
    last_scan_error text        NOT NULL DEFAULT '',
    video_count     integer     NOT NULL DEFAULT 0,
    deleted_at      timestamptz,
    created_at      timestamptz NOT NULL DEFAULT now(),
    updated_at      timestamptz NOT NULL DEFAULT now(),
    UNIQUE (workspace_id, external_id)
);
CREATE INDEX source_scan_idx ON source (workspace_id, is_active, last_scan_at);
```

Two identifiers are kept on purpose: `url` is what the operator typed (so the
UI can show it back), `external_id` is the canonical form resolved by the
fetcher (so matching is exact). `video_count` is a cached count, refreshed on
scan — the authoritative count is always a query against `catalog_video`.

```sql
CREATE TABLE catalog_video (
    id              bigint GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    workspace_id    bigint      NOT NULL REFERENCES workspace(id) ON DELETE CASCADE,
    source_id       bigint      NOT NULL REFERENCES source(id) ON DELETE CASCADE,
    video_id        text        NOT NULL,        -- 11-character YouTube id
    title           text        NOT NULL DEFAULT '',
    duration_sec    integer,
    published_at    timestamptz,
    thumbnail_url   text        NOT NULL DEFAULT '',
    live_status     text        NOT NULL DEFAULT 'unknown',
    availability    text        NOT NULL DEFAULT 'unknown'
                    CHECK (availability IN
                      ('available','unavailable','private','unknown')),
    -- Hydrated lazily. NULL means "not hydrated yet", which is different from "".
    description     text,
    tags            text[],
    view_count      bigint,
    like_count      bigint,
    category        text,
    hydrated_at     timestamptz,
    -- Operator flags. `starred` doubles as the retention pin (never auto-delete).
    starred         boolean     NOT NULL DEFAULT false,
    ignored         boolean     NOT NULL DEFAULT false,
    first_seen_at   timestamptz NOT NULL DEFAULT now(),
    last_seen_at    timestamptz NOT NULL DEFAULT now(),
    created_at      timestamptz NOT NULL DEFAULT now(),
    updated_at      timestamptz NOT NULL DEFAULT now(),
    UNIQUE (source_id, video_id)
);
CREATE INDEX catalog_video_source_date_idx
    ON catalog_video (source_id, published_at DESC);
CREATE INDEX catalog_video_lookup_idx
    ON catalog_video (workspace_id, video_id);
CREATE INDEX catalog_video_hydrate_idx
    ON catalog_video (source_id, hydrated_at NULLS FIRST);
```

**Why the uniqueness is `(source_id, video_id)`, not `(workspace_id, video_id)`:**
the same video legitimately appears in several sources (a channel and a curated
playlist). Catalogue state is therefore per source, while delivery state is
global per `(video_id, destination)` — a video seen in two sources is catalogued
twice and delivered once. This is exactly what `FEATURE_CATALOG_AND_BACKFILL.md`
concluded independently in the legacy, and it is INV-9.

`last_seen_at` is how a video that disappears from the feed is detected without
deleting the row: a scan that omits a previously seen video sets
`availability = 'unavailable'` and leaves everything else intact.

`catalog_video_hydrate_idx` exists so the hydrate worker can find its next
batch with an index scan rather than a table scan.

## 6. Group 4 — Pipelines

```sql
CREATE TABLE download_profile (
    id                 bigint GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    workspace_id       bigint      NOT NULL REFERENCES workspace(id) ON DELETE CASCADE,
    name               text        NOT NULL,
    max_height         integer     NOT NULL DEFAULT 0,     -- 0 = no cap
    container          text        NOT NULL DEFAULT 'mp4',
    video_codec        text        NOT NULL DEFAULT 'any',
    audio_codec        text        NOT NULL DEFAULT 'any',
    write_subs         boolean     NOT NULL DEFAULT true,
    sub_langs          text[]      NOT NULL DEFAULT '{en}',
    write_thumbnail    boolean     NOT NULL DEFAULT true,
    write_info_json    boolean     NOT NULL DEFAULT true,
    skip_shorts        boolean     NOT NULL DEFAULT false,
    shorts_max_seconds integer     NOT NULL DEFAULT 60,
    skip_live          boolean     NOT NULL DEFAULT true,
    extra_ytdlp_opts   jsonb       NOT NULL DEFAULT '{}'::jsonb,  -- escape hatch
    created_at         timestamptz NOT NULL DEFAULT now(),
    updated_at         timestamptz NOT NULL DEFAULT now(),
    UNIQUE (workspace_id, name)
);
```

Compared with the legacy profile, `audio_only` and the embed flags are gone — we
always upload video and we never re-encode (D15).

```sql
CREATE TABLE pipeline (
    id                  bigint GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    workspace_id        bigint      NOT NULL REFERENCES workspace(id) ON DELETE CASCADE,
    name                text        NOT NULL,
    description         text        NOT NULL DEFAULT '',
    status              text        NOT NULL DEFAULT 'draft'
                        CHECK (status IN ('draft','active','paused')),
    priority            integer     NOT NULL DEFAULT 100,   -- lower runs first
    download_profile_id bigint      REFERENCES download_profile(id) ON DELETE SET NULL,
    default_privacy     text        NOT NULL DEFAULT 'unlisted'
                        CHECK (default_privacy IN ('private','unlisted','public')),
    provenance_marker   boolean     NOT NULL DEFAULT true,   -- D2
    -- Retention policy. `keep` short-circuits: no scans, no queries, no UI.
    retention_mode      text        NOT NULL DEFAULT 'keep'
                        CHECK (retention_mode IN
                          ('keep','immediate','after_n_jobs','after_hours')),
    retention_n         integer     NOT NULL DEFAULT 2  CHECK (retention_n >= 1),
    retention_hours     integer     NOT NULL DEFAULT 24 CHECK (retention_hours >= 1),
    deleted_at          timestamptz,
    created_at          timestamptz NOT NULL DEFAULT now(),
    updated_at          timestamptz NOT NULL DEFAULT now(),
    UNIQUE (workspace_id, name)
);
CREATE INDEX pipeline_run_idx ON pipeline (workspace_id, status, priority);
```

`status` starts at `draft`, so a half-configured pipeline cannot run. Only an
operator moving it to `active` begins work — which is the explicit answer to the
legacy's open question about whether backfill should start automatically.

```sql
CREATE TABLE pipeline_source (
    id                           bigint GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    workspace_id                 bigint      NOT NULL REFERENCES workspace(id) ON DELETE CASCADE,
    pipeline_id                  bigint      NOT NULL REFERENCES pipeline(id) ON DELETE CASCADE,
    source_id                    bigint      NOT NULL REFERENCES source(id)   ON DELETE CASCADE,
    mode                         text        NOT NULL DEFAULT 'monitor'
                                 CHECK (mode IN ('monitor','backfill')),
    priority                     integer     NOT NULL DEFAULT 100,
    daily_cap                    integer     CHECK (daily_cap IS NULL OR daily_cap > 0),
    backfill_state               text        NOT NULL DEFAULT 'not_started'
                                 CHECK (backfill_state IN
                                   ('not_started','running','paused','complete','stopped')),
    backfill_cursor_published_at timestamptz,
    backfill_done_count          integer     NOT NULL DEFAULT 0,
    backfill_total_count         integer,
    created_at                   timestamptz NOT NULL DEFAULT now(),
    updated_at                   timestamptz NOT NULL DEFAULT now(),
    UNIQUE (pipeline_id, source_id)
);
CREATE INDEX pipeline_source_backfill_idx
    ON pipeline_source (pipeline_id, backfill_state);
```

**The backfill queue is a cursor, not a list.** This is the direct fix for F-04
and F-05: the legacy kept `backfill_queue` and `videos_seen` as JSON blobs that
could not be queried, could not be trusted, and grew without bound. Here, "what
is left to backfill" is a query against `catalog_video` filtered by the cursor —
so it is always correct, always resumable from any point, and needs no
maintenance.

`daily_cap` is nullable: `NULL` means "governed only by the destination's own
`daily_max` and quota". It exists because a source producing many short videos
may need a tighter limit than the destination as a whole.

```sql
CREATE TABLE destination (
    id                    bigint GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    workspace_id          bigint      NOT NULL REFERENCES workspace(id) ON DELETE CASCADE,
    authorized_channel_id bigint      NOT NULL
                          REFERENCES authorized_channel(id) ON DELETE RESTRICT,
    label                 text        NOT NULL,
    platform              text        NOT NULL DEFAULT 'youtube'
                          CHECK (platform = 'youtube'),
    default_privacy       text        NOT NULL DEFAULT 'unlisted'
                          CHECK (default_privacy IN ('private','unlisted','public')),
    daily_max             integer     NOT NULL DEFAULT 6 CHECK (daily_max > 0),
    enabled               boolean     NOT NULL DEFAULT true,
    last_sync_at          timestamptz,
    last_sync_error       text        NOT NULL DEFAULT '',
    deleted_at            timestamptz,
    created_at            timestamptz NOT NULL DEFAULT now(),
    updated_at            timestamptz NOT NULL DEFAULT now(),
    UNIQUE (workspace_id, label)
);
CREATE INDEX destination_enabled_idx ON destination (workspace_id, enabled);
```

`platform` carries a `CHECK` permitting exactly one value in v1. Adding a
platform later is a deliberate migration, never an accident. `ON DELETE
RESTRICT` on the channel is intentional: a destination cannot be orphaned into
a state where it has nowhere to deliver.

```sql
CREATE TABLE pipeline_destination (
    id                      bigint GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    workspace_id            bigint      NOT NULL REFERENCES workspace(id) ON DELETE CASCADE,
    pipeline_id             bigint      NOT NULL REFERENCES pipeline(id) ON DELETE CASCADE,
    destination_id          bigint      NOT NULL REFERENCES destination(id) ON DELETE CASCADE,
    enabled                 boolean     NOT NULL DEFAULT true,
    priority                integer     NOT NULL DEFAULT 100,
    privacy_override        text
                            CHECK (privacy_override IN ('private','unlisted','public')),
    retention_mode_override text
                            CHECK (retention_mode_override IN
                              ('keep','immediate','after_n_jobs','after_hours')),
    created_at              timestamptz NOT NULL DEFAULT now(),
    updated_at              timestamptz NOT NULL DEFAULT now(),
    UNIQUE (pipeline_id, destination_id)
);
CREATE INDEX pipeline_destination_idx
    ON pipeline_destination (pipeline_id, enabled);
```

`destination` lives at workspace level and is attached to pipelines through this
join, so one authorised channel can serve several pipelines without being
duplicated. By D14 the v1 rule is simply: every enabled row here receives every
video from every source of the pipeline. `retention_mode_override` exists
because "keep the last N jobs" must remain computable for a destination that
participates in more than one pipeline.

## 7. Group 5 — Work

```sql
CREATE TABLE job (
    id               bigint GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    workspace_id     bigint      NOT NULL REFERENCES workspace(id) ON DELETE CASCADE,
    pipeline_id      bigint      NOT NULL REFERENCES pipeline(id) ON DELETE CASCADE,
    source_id        bigint      REFERENCES source(id) ON DELETE SET NULL,
    source_video_id  text        NOT NULL,          -- 11-character YouTube id
    intent           text        NOT NULL DEFAULT 'upload'
                     CHECK (intent IN ('upload','rehydrate','inspect')),
    status           text        NOT NULL DEFAULT 'queued'
                     CHECK (status IN
                       ('queued','claimed','downloading','downloaded','uploading',
                        'uploaded','failed_transient','failed_permanent',
                        'skipped','cancelled')),
    priority         integer     NOT NULL DEFAULT 100,   -- lower runs first
    attempt_count    integer     NOT NULL DEFAULT 0,
    claimed_by       text        NOT NULL DEFAULT '',
    claimed_at       timestamptz,
    claim_expires_at timestamptz,
    error_code       text        NOT NULL DEFAULT '',
    error_message    text        NOT NULL DEFAULT '',
    skip_reason      text        NOT NULL DEFAULT '',
    bytes_downloaded bigint      NOT NULL DEFAULT 0,
    started_at       timestamptz,
    finished_at      timestamptz,
    created_at       timestamptz NOT NULL DEFAULT now(),
    updated_at       timestamptz NOT NULL DEFAULT now()
);

-- One live job per (pipeline, video, intent). Cancelled and skipped jobs are
-- excluded so the operator can deliberately re-run one.
CREATE UNIQUE INDEX job_live_unique
    ON job (workspace_id, pipeline_id, source_video_id, intent)
    WHERE status NOT IN ('cancelled', 'skipped');

CREATE INDEX job_claim_idx        ON job (priority, created_at) WHERE status = 'queued';
CREATE INDEX job_pipeline_idx     ON job (workspace_id, pipeline_id, status);
CREATE INDEX job_video_idx        ON job (workspace_id, source_video_id);
CREATE INDEX job_stale_claim_idx  ON job (status, claim_expires_at);
```

**The claim query.** This is the piece that replaces the legacy's read-then-write
race (P11). One statement, atomic, safe with many workers:

```sql
UPDATE job
   SET status = 'claimed', claimed_by = :worker, claimed_at = now(),
       claim_expires_at = now() + interval '15 minutes'
 WHERE id = (
     SELECT id FROM job
      WHERE status = 'queued'
      ORDER BY priority, created_at
      FOR UPDATE SKIP LOCKED
      LIMIT 1)
RETURNING *;
```

`claim_expires_at` makes a crashed worker self-healing: the recovery pass returns
expired claims to `queued`. `inspect` is a job intent for "fetch and record
metadata without delivering", which manual URL entry uses.

## 8. Group 6 — Delivery truth

```sql
CREATE TABLE delivery (
    id                    bigint GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    workspace_id          bigint      NOT NULL REFERENCES workspace(id) ON DELETE CASCADE,
    source_video_id       text        NOT NULL,
    destination_id        bigint      NOT NULL REFERENCES destination(id) ON DELETE RESTRICT,
    -- CURRENT state only. Every value these fields ever held is preserved in
    -- delivery_attempt, which is what makes them effectively write-once.
    status                text        NOT NULL DEFAULT 'not_delivered'
                          CHECK (status IN
                            ('not_delivered','queued','uploading','uploaded',
                             'failed','removed')),
    destination_video_id  text,
    destination_url       text        NOT NULL DEFAULT '',
    destination_title     text        NOT NULL DEFAULT '',   -- as we uploaded it
    source_title_snapshot text        NOT NULL DEFAULT '',   -- title at upload time
    provenance_marker     text        NOT NULL DEFAULT '',
    match_method          text        NOT NULL DEFAULT 'ledger'
                          CHECK (match_method IN
                            ('ledger','marker','fingerprint','manual')),
    privacy               text        NOT NULL DEFAULT 'unlisted',
    uploaded_at           timestamptz,
    error_message         text        NOT NULL DEFAULT '',
    last_job_id           bigint      REFERENCES job(id) ON DELETE SET NULL,
    created_at            timestamptz NOT NULL DEFAULT now(),
    updated_at            timestamptz NOT NULL DEFAULT now(),
    UNIQUE (workspace_id, source_video_id, destination_id)
);

CREATE INDEX delivery_destination_idx ON delivery (destination_id, status);
CREATE INDEX delivery_video_idx       ON delivery (workspace_id, source_video_id);
CREATE INDEX delivery_retention_idx   ON delivery (destination_id, uploaded_at DESC);
```

`ON DELETE RESTRICT` on the destination is deliberate: a destination with
delivery history cannot be hard-deleted, only soft-deleted. That is D12 and
INV-4, enforced by the database rather than by discipline.

`source_title_snapshot` exists because the source channel can retitle or delete a
video after we delivered it, and history must remain readable. The legacy stored
the source title (`videos.original_title`) but never stored what it actually
uploaded to the other side, so the two halves of a delivery could never be
compared — that is why reconciliation was impossible (D-13).

`delivery_retention_idx` is the index the retention evaluator walks to compute
"the last N completed jobs" without a table scan.

```sql
CREATE TABLE delivery_attempt (
    id                   bigint GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    workspace_id         bigint      NOT NULL REFERENCES workspace(id) ON DELETE CASCADE,
    delivery_id          bigint      NOT NULL REFERENCES delivery(id) ON DELETE CASCADE,
    attempt_no           integer     NOT NULL CHECK (attempt_no >= 1),
    status               text        NOT NULL
                         CHECK (status IN
                           ('uploading','uploaded','failed','cancelled')),
    origin               text        NOT NULL DEFAULT 'system'
                         CHECK (origin IN ('system','retry','manual')),
    -- The values THIS attempt produced. This table is the immutable record.
    destination_video_id text,
    destination_url      text        NOT NULL DEFAULT '',
    privacy              text        NOT NULL DEFAULT 'unlisted',
    http_status          integer,
    error_code           text        NOT NULL DEFAULT '',
    error_message        text        NOT NULL DEFAULT '',
    bytes_sent           bigint      NOT NULL DEFAULT 0,
    duration_ms          integer,
    started_at           timestamptz NOT NULL DEFAULT now(),
    finished_at          timestamptz,
    UNIQUE (delivery_id, attempt_no)
);
CREATE INDEX delivery_attempt_recent_idx
    ON delivery_attempt (delivery_id, attempt_no DESC);
```

**The write-once resolution in practice.** Suppose we deliver video *X* to a
destination and get back `destination_video_id = abc123`. Attempt 1 records
`abc123`. The operator later deletes that video on YouTube; reconciliation
detects it and a re-upload produces `xyz789`. Attempt 2 records `xyz789`, and
`delivery.destination_video_id` is updated to the current truth. The value
`abc123` still exists in attempt 1 forever. So the identifying fields behave as
write-once *per attempt*, there is a complete audit trail, and no second
parallel table is needed to preserve history.

`origin` distinguishes an automatic retry from an operator-initiated re-upload.
Without it, "why did this upload happen twice?" has no answer, which the legacy
demonstrated by having no answer for the same question.

```sql
CREATE TABLE destination_inventory (
    id                   bigint GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    workspace_id         bigint      NOT NULL REFERENCES workspace(id) ON DELETE CASCADE,
    destination_id       bigint      NOT NULL REFERENCES destination(id) ON DELETE CASCADE,
    destination_video_id text        NOT NULL,
    title                text        NOT NULL DEFAULT '',
    description_excerpt  text        NOT NULL DEFAULT '',
    published_at         timestamptz,
    privacy              text        NOT NULL DEFAULT 'unknown'
                         CHECK (privacy IN
                           ('public','unlisted','private','unknown')),
    duration_sec         integer,
    provenance_marker    text,               -- parsed from the description, if present
    matched_delivery_id  bigint      REFERENCES delivery(id) ON DELETE SET NULL,
    match_method         text        NOT NULL DEFAULT 'none'
                         CHECK (match_method IN
                           ('none','marker','ledger','fingerprint')),
    is_present           boolean     NOT NULL DEFAULT true,
    first_observed_at    timestamptz NOT NULL DEFAULT now(),
    last_observed_at     timestamptz NOT NULL DEFAULT now(),
    UNIQUE (destination_id, destination_video_id)
);
CREATE INDEX destination_inventory_unclaimed_idx
    ON destination_inventory (destination_id, matched_delivery_id)
    WHERE matched_delivery_id IS NULL;
CREATE INDEX destination_inventory_title_idx
    ON destination_inventory (destination_id, title);
```

This table is the capability the legacy never had (D-13). Three rules govern it:

1. **It is observation, not ownership.** A sync writes what the YouTube API
   returned. Nothing here is authoritative about what *we* did — that is
   `delivery`.
2. **A sync never deletes rows.** A video that is no longer returned sets
   `is_present = false` and stops updating `last_observed_at`. This is what makes
   "the destination copy is gone" a detectable fact rather than a guess.
3. **`matched_delivery_id IS NULL` means unclaimed.** Unclaimed content is
   surfaced for review and never auto-adopted into a delivery (INV-8) — the
   legacy's own catalogue RFC reached the same conclusion about fuzzy matching.

`provenance_marker` is stored rather than recomputed, so a marker whose format
later changes still reads correctly in history.

```sql
CREATE TABLE quota_usage (
    id             bigint GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    workspace_id   bigint      NOT NULL REFERENCES workspace(id) ON DELETE CASCADE,
    destination_id bigint      NOT NULL REFERENCES destination(id) ON DELETE CASCADE,
    quota_date     date        NOT NULL,     -- YouTube quota day: midnight Pacific
    uploads_used   integer     NOT NULL DEFAULT 0 CHECK (uploads_used >= 0),
    units_used     integer     NOT NULL DEFAULT 0 CHECK (units_used >= 0),
    updated_at     timestamptz NOT NULL DEFAULT now(),
    UNIQUE (destination_id, quota_date)
);
CREATE INDEX quota_usage_recent_idx
    ON quota_usage (destination_id, quota_date DESC);
```

`quota_date` is a **date in the YouTube quota timezone**, not a UTC midnight.
This is the direct fix for D-03, where the legacy reset its counter at UTC
midnight while YouTube resets at midnight Pacific — an up-to-eight-hour window
in which the app believed it had budget it did not have.

`units_used` is tracked alongside `uploads_used` because units are the real
constraint: an upload costs ~1 600 units, metadata and thumbnail ~50, against
10 000 per day. Counting uploads alone cannot explain a quota exhaustion, and
being able to say *why* the budget ran out is exactly the operational clarity
that was missing.

## 9. Group 7 — Media and storage

```sql
CREATE TABLE storage_root (
    id              bigint GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    workspace_id    bigint      NOT NULL REFERENCES workspace(id) ON DELETE CASCADE,
    label           text        NOT NULL,
    path            text        NOT NULL,
    role            text        NOT NULL DEFAULT 'hot'
                    CHECK (role IN ('hot','cold')),
    priority        integer     NOT NULL DEFAULT 100,      -- lower fills first
    min_free_bytes  bigint      NOT NULL DEFAULT 10737418240
                    CHECK (min_free_bytes >= 0),           -- 10 GiB floor
    is_mounted      boolean     NOT NULL DEFAULT true,
    free_bytes      bigint,
    total_bytes     bigint,
    last_checked_at timestamptz,
    is_active       boolean     NOT NULL DEFAULT true,
    created_at      timestamptz NOT NULL DEFAULT now(),
    updated_at      timestamptz NOT NULL DEFAULT now(),
    UNIQUE (workspace_id, path)
);
CREATE INDEX storage_root_pick_idx
    ON storage_root (workspace_id, is_active, role, priority);
```

`is_mounted = false` is a real state, not an error: a cold root that is currently
detached. Every asset on it becomes `archive_offline`, which is what stops a
re-attached drive from triggering a mass re-download (F-52).

```sql
CREATE TABLE media_asset (
    id                 bigint GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    workspace_id       bigint      NOT NULL REFERENCES workspace(id) ON DELETE CASCADE,
    source_video_id    text        NOT NULL,
    source_id          bigint      REFERENCES source(id) ON DELETE SET NULL,
    job_id             bigint      REFERENCES job(id) ON DELETE SET NULL,
    storage_root_id    bigint      REFERENCES storage_root(id) ON DELETE SET NULL,
    materialization_no integer     NOT NULL DEFAULT 1 CHECK (materialization_no >= 1),
    path               text        NOT NULL,
    filename           text        NOT NULL DEFAULT '',
    size_bytes         bigint      NOT NULL DEFAULT 0,
    sha256             text        NOT NULL DEFAULT '',
    duration_sec       integer,
    state              text        NOT NULL DEFAULT 'expected'
                       CHECK (state IN ('expected','downloading','on_disk',
                                        'archive_offline','deleted','failed')),
    pinned_until       timestamptz,
    pinned_reason      text        NOT NULL DEFAULT '',
    downloaded_at      timestamptz,
    delete_after       timestamptz,
    deleted_at         timestamptz,
    delete_reason      text        NOT NULL DEFAULT '',
    created_at         timestamptz NOT NULL DEFAULT now(),
    updated_at         timestamptz NOT NULL DEFAULT now(),
    UNIQUE (workspace_id, source_video_id, materialization_no)
);
CREATE INDEX media_asset_state_idx ON media_asset (workspace_id, state);
CREATE INDEX media_asset_video_idx ON media_asset (workspace_id, source_video_id);
CREATE INDEX media_asset_due_idx   ON media_asset (delete_after) WHERE state = 'on_disk';
CREATE INDEX media_asset_root_idx  ON media_asset (storage_root_id, state);
```

`materialization_no` is what makes re-download honest: copy 1 was the original,
copy 2 is a later re-download, and `sha256` records that they need not be
byte-identical. `delete_after` is a computed timestamp rather than a rule that
is re-evaluated forever — so a retention decision is made once, is visible, and
can be undone before it fires.

```sql
CREATE TABLE media_event (
    id              bigint GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    workspace_id    bigint      NOT NULL REFERENCES workspace(id) ON DELETE CASCADE,
    media_asset_id  bigint      REFERENCES media_asset(id) ON DELETE SET NULL,
    source_video_id text        NOT NULL,
    event           text        NOT NULL
                    CHECK (event IN
                      ('created','verified','pinned','unpinned','delete_scheduled',
                       'delete_skipped','deleted','rehydrated','archive_offline')),
    reason          text        NOT NULL DEFAULT '',
    bytes           bigint      NOT NULL DEFAULT 0,
    actor           text        NOT NULL DEFAULT 'system',
    created_at      timestamptz NOT NULL DEFAULT now()
);
CREATE INDEX media_event_recent_idx ON media_event (workspace_id, created_at DESC);
CREATE INDEX media_event_video_idx  ON media_event (workspace_id, source_video_id);
```

This table turns "the disk is full and nobody knows why" into *"4.2 GB was freed
at 03:11 because pipeline 3 reached N = 2"*. `ON DELETE SET NULL` is deliberate:
the audit of a deletion must survive the row being deleted.

## 10. Group 8 — Operations

```sql
CREATE TABLE worker_heartbeat (
    worker_id      text        PRIMARY KEY,
    workspace_id   bigint      REFERENCES workspace(id) ON DELETE CASCADE,
    kind           text        NOT NULL DEFAULT '',
    status         text        NOT NULL DEFAULT 'idle'
                   CHECK (status IN ('idle','busy','error','stopped')),
    detail         text        NOT NULL DEFAULT '',
    current_job_id bigint      REFERENCES job(id) ON DELETE SET NULL,
    started_at     timestamptz NOT NULL DEFAULT now(),
    last_beat_at   timestamptz NOT NULL DEFAULT now(),
    host           text        NOT NULL DEFAULT '',
    pid            integer
);
CREATE INDEX worker_heartbeat_stale_idx ON worker_heartbeat (last_beat_at);
```

A worker that has not beaten within three intervals is displayed as stale. That
is how a silently dead worker becomes visible, rather than being inferred from a
queue that stopped moving.

```sql
CREATE TABLE audit_event (
    id           bigint GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    workspace_id bigint      REFERENCES workspace(id) ON DELETE SET NULL,
    actor        text        NOT NULL DEFAULT 'system',
    entity       text        NOT NULL,
    entity_id    text        NOT NULL DEFAULT '',
    action       text        NOT NULL,
    detail       jsonb       NOT NULL DEFAULT '{}'::jsonb,
    created_at   timestamptz NOT NULL DEFAULT now()
);
CREATE INDEX audit_event_recent_idx ON audit_event (created_at DESC);
CREATE INDEX audit_event_entity_idx ON audit_event (entity, entity_id);
```

`workspace_id` is `SET NULL` so the trail outlives the workspace it describes —
an audit log that disappears with its subject is not an audit log. `detail` is
`jsonb` because it is the one genuinely schema-less payload in the system, and an
audit entry must be able to record whatever was true at the time.

## 11. Bootstrapping

Created by a **data migration**, never by hand-written SQL, so a fresh install is
reproducible and reviewable:

| Created | Content |
|---|---|

| `workspace_member` | one `owner` row linking the first user |

## 12. Maintenance and migration policy

**Purge is explicit and never automatic.** Configuration entities (`pipeline`,
`source`, `destination`) can be soft-deleted freely. History tables have no
cascading path from them, so removing a pipeline can never erase what happened.
A single maintenance command purges history deliberately, by workspace and
cut-off date, and reports what it will remove before doing it.

**Migration policy**

1. One migration per concern, with a descriptive name.
2. A shipped migration is never edited. A mistake is corrected by a new
   migration.
3. Renames use Django's `RenameModel`/`RenameField` so the rename is recorded
   as a rename rather than as a drop-and-add.
4. Destructive operations (dropping a column, narrowing a type) require the
   data-loss warning Django asks for to be committed alongside the change.
5. `03_DATABASE_SCHEMA.md` is updated in the same commit as the model change —
   the rule from §1.
